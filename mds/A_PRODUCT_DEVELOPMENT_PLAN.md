# ICE STOCK — A 담당 개발 진행 계획

## 1. 목표와 개발 원칙

유림(A)의 Product / Product Detail을 기존 SAPUI5 프로젝트에서 구현한다. 화면 구조·표시 내용·기능은 `figma-make-source/src/App.tsx`를 기준으로 한다. CSS까지 동일하게 재현하지 않고 SAPUI5 기본 스타일과 컨트롤을 사용한다.

사용자가 코드를 읽으며 공부할 수 있도록 기본 XML 바인딩, JSONModel, 명확한 이름의 이벤트 함수와 계산 함수를 사용한다. 불필요한 추상화, 복잡한 공통 구조, 과도한 파일 분리를 피하고 주요 처리에는 이해를 돕는 짧은 설명을 덧붙인다.

현재 사이드바는 유지한다. 최종 메뉴 통합과 대시보드 조립은 팀원들의 개발이 끝난 이후 별도 작업으로 진행하므로 이번 개발 계획에서 제외한다. Product Detail은 상품 목록에서 진입하는 하위 화면으로 구현한다.

전달받은 팀 협업 가이드는 담당 범위의 참고 자료로 사용하되, 이 계획에는 사용자가 추가로 설명한 현재 개발 방식을 우선 반영했다. 이번 수정은 계획 문서에만 적용하며 앱 코드는 변경하지 않는다.

## 2. 수정 범위와 협업 경계

| 구분 | 파일 | 작업 내용 |
| --- | --- | --- |
| A 핵심 기능 | `webapp/view/Product.view.xml` | 상품 목록·검색·필터·관리 UI |
| A 핵심 기능 | `webapp/controller/Product.controller.js` | 상품 CRUD와 목록용 데이터 가공 |
| A 핵심 기능 | `webapp/view/ProductDetail.view.xml` | 상품 정보·재고·판매 요약·이력 UI |
| A 핵심 기능 | `webapp/controller/ProductDetail.controller.js` | 선택 상품 조회와 상세 데이터 가공 |
| A 라우팅 | `webapp/manifest.json` | 상품·상세 화면 연결에 필요한 범위만 변경 |
| A 신규 파일 | 상품 전용 XML Fragment 등 | 등록·수정 폼 등 필요한 파일만 추가 |

이번 작업에서는 다음 파일을 직접 수정하지 않는다.

- B: StockMovement View·Controller, `Component.js`, `model/models.js`, `model/mockData.json`, `util/dashboardData.js`
- C·D·E: `view/dashboard/`, `controller/dashboard/` 내부 파일
- 공통 화면: App View·Controller, `MainView.view.xml`
- 디자인 참고 원본: `figma-make-source/`

스타일은 SAPUI5 기본 테마와 여백 클래스를 우선 사용한다. 꼭 필요한 CSS만 상품 화면 범위에 제한하여 추가하고 공통 스타일은 바꾸지 않는다. 신규 스타일 연결이 필요하면 A 담당 manifest에서 필요한 범위만 변경한다.

## 3. 현재 상태

- Product와 Product Detail View·Controller는 기본 골격 상태다.
- 공통 `inventory` JSONModel에서 `mockData.json`을 비동기로 읽는다.
- 상품 상세 라우트가 없으며 상품 target과 실제 View 파일명의 대소문자 점검이 필요하다.
- Figma Make 소스에는 상품 목록, 등록·수정 모달, 상세 화면 구현이 있다.
- C·D·E는 각자 Controller에서 집계 후 데이터를 JSONModel로 만들어 사용하고 있다. A도 같은 방식으로 화면 데이터를 가공한다.
- JSONModel의 실행 중 데이터 변경은 원본 JSON 파일에 영구 저장되지 않는다.

## 4. 개발 순서

### 1단계 — 화면 항목과 A 전용 JSONModel 설계

Figma Make의 `Products`, `ProductDialog`, `Detail`을 읽고 화면 구조·표시 내용·동작을 정리한다. React 내부 변환 필드명 대신 기존 SAPUI5 원본 필드명을 유지한다.

| 데이터 | 사용할 필드 |
| --- | --- |
| 상품 | `productId`, `productName`, `categoryId`, `purchasePrice`, `sellingPrice`, `stock`, `safetyStock`, `unit`, `active` |
| 카테고리 | `categoryId`, `categoryName` |
| 입출고 | `movementId`, `productId`, `date`, `type`, `reason`, `quantity`, `beforeStock`, `afterStock`, `note` |
| 판매 | `salesId`, `productId`, `date`, `quantity`, `totalAmount`, `totalCost`, `profit` |

상품 Controller에서 화면용 JSONModel을 직접 만들고 아래 값을 계산하여 상품 행 데이터에 담는다. B의 집계 데이터나 API 제공을 기다리지 않는다.

| 가공 항목 | 계산 방식 |
| --- | --- |
| 판매수량 | `/sales`에서 같은 `productId`의 `quantity` 합계. 판매 이력이 없으면 0 |
| 재고 상태 | `stock <= safetyStock`이면 부족, 그 외 정상 |
| 필요수량 | `Math.max(safetyStock - stock, 0)` |

카테고리명 등 표시용 값도 필요하면 함께 담는다. 원본 필드명은 유지하고 가공 값은 별도 필드로 추가한다. 검색 조건·정렬·등록 폼·선택 상품 ID도 A 화면용 모델에서 관리하며 원본 inventory에 임의의 화면 상태를 추가하지 않는다.

조회·정렬에는 가공 모델을 사용한다. 저장 시에는 `productId`로 원본 inventory 상품을 찾아 변경한 뒤 가공 모델을 다시 만든다. 정렬된 테이블의 행 인덱스를 원본 배열 인덱스로 사용하지 않는다.

**완료 기준:** 표시 항목과 원본 필드의 관계, 세 가지 가공 값, CRUD 규칙이 정리되어 있다.

### 2단계 — 상품 목록과 상세 화면 이동 연결

- manifest의 product target을 실제 `Product.view.xml`에 정확히 연결한다.
- 예를 들어 `product/{productId}` 패턴의 `productDetail` 라우트를 추가한다.
- 배열 인덱스 대신 `productId`로 상품을 식별한다.
- 상세 화면에서 URL의 ID로 상품을 찾아 바인딩한다.
- 모델 로딩 전 진입, 새로고침, 잘못된 ID, 존재하지 않는 상품을 처리한다.
- 목록으로 돌아오면 검색·필터·정렬 상태를 유지한다.

**완료 기준:** 목록 → 상세 → 목록 이동과 상세 URL 직접 진입이 동작한다.

### 3단계 — Product 목록 UI와 검색·필터 구현

Figma의 정보 구조를 따라 SAPUI5 컨트롤로 제목·설명, 등록 버튼, 검색·필터, 결과 건수, 테이블을 배치한다.

- 상품코드·상품명 검색
- 카테고리·재고 상태 필터
- 기본순·재고 부족순·판매량 높은순 등 참조 소스의 정렬
- 상품코드, 상품명, 카테고리, 매입·매출단가, 현재 재고, 안전재고, 판매수량, 재고 상태, 필요수량, 관리 버튼 표시
- 상세·수정·비활성화 버튼
- 검색 결과 없음과 좁은 화면 처리

판매수량·재고 상태·필요수량은 1단계의 A 전용 JSONModel에 바인딩한다. 판매량 정렬에도 직접 가공한 값을 사용한다. 데이터 로딩 완료 후 가공 모델을 생성하도록 구현한다.

**완료 기준:** 실제 원본 데이터와 가공 값이 표시되고 검색·필터·정렬이 함께 동작한다.

### 4단계 — 상품 등록·수정·비활성화 구현

등록·수정 폼은 상품 전용 XML Fragment로 분리한다. 임시 폼 모델에서 입력받고 저장할 때만 inventory에 반영하여 취소 시 원본이 바뀌지 않게 한다.

- 고유 상품코드, 필수 상품명, 유효 카테고리를 검증한다.
- 수량은 정수·0 이상, 단가는 유한한 숫자·0 이상인지 확인한다.
- 비활성 상품까지 포함하여 코드 중복을 검사하고 자동 코드 생성 시 충돌을 방지한다.
- Figma 기준으로 기존 상품코드와 최초 등록한 매입·매출단가는 수정하지 않는다.
- A 수정 폼에서 재고를 직접 증감하지 않는다. 최초 재고와 이력 생성 규칙은 추후 B와 협의하며 임의로 입출고 이력을 만들지 않는다.
- 삭제는 확인창을 거쳐 `active: false`로 비활성화하고 기존 판매·입출고 이력은 보존한다.
- 기본 목록에서는 활성 상품만 표시한다.
- `setProperty` 등으로 원본 모델에 변경을 알리고 A의 화면용 가공 모델도 다시 계산한다.

**완료 기준:** 등록·수정·취소·비활성화와 입력 검증이 동작한다. 원본 JSON 파일 자체는 덮어쓰지 않는다.

### 5단계 — Product Detail 구현

- 상품코드·상품명·카테고리·판매 상태·단가 표시
- 현재 재고·안전재고·재고 금액·보충 필요수량 표시
- 판매수량, 누적 매출액·매출원가·매출총이익·마진율 표시
- 선택한 productId의 입출고 이력만 표시
- 금액·수량·날짜·입출고 상태 표시 형식 정리
- 매출 0, 이력 없음, 비활성 상품 처리

상품별 요약도 A Controller에서 원본 데이터를 읽어 직접 계산하고 상세 화면용 JSONModel에 담는다. B의 통계 유틸리티나 dashboard 모델에 의존하지 않는다. 읽기 쉬운 작은 계산 함수로 작성하며 상세 진입 시 현재 원본 데이터로 계산한다.

**완료 기준:** 선택 상품의 정보·요약·이력만 표시된다. B의 입출고 이후 화면 갱신 연동은 추후 협의 사항으로 남긴다.

### 6단계 — UI5 스타일 정리와 검증

SAPUI5 기본 테이블, 입력 컨트롤, Dialog, ObjectStatus 등으로 구성한다. Figma와 정보 구조·내용을 맞추되 색상·테두리·픽셀 단위 간격까지 맞추지 않는다. 맞춤 CSS보다 기본 레이아웃과 여백 클래스를 우선한다.

검증 시나리오:

- 정상 등록과 중복 코드·빈 이름·음수·잘못된 숫자 차단
- 수정 취소 시 원본 유지, 저장 후 목록·상세 데이터 갱신
- 비활성화 후 활성 목록 제외와 기존 이력 보존
- 검색·카테고리·재고 필터 조합과 초기화
- 재고 0, 안전재고와 동일, 판매 없음, 검색 결과 없음
- 판매수량·재고 상태·필요수량 계산 및 상품 저장 후 가공 모델 재계산
- 정렬 이후 정확한 상품 상세 이동, 직접 URL 진입과 잘못된 ID 처리
- 기존 입출고·대시보드 화면에 영향이 없는지 확인

`npm run lint`, `npm run build`를 실행하고 A 변경으로 생긴 오류와 기존 오류를 구분한다. 자동화가 필요하면 입력 검증·ID 생성 등 실제 오류를 막는 핵심 로직에 집중한다.

**완료 기준:** A 기능과 자체 데이터 가공 검증이 통과하고 변경 파일이 A 범위에 한정된다. 팀 간 연동과 메뉴 통합은 완료 조건에 포함하지 않는다.

## 5. 추후 B와 상의할 항목

지금 B에게 전달하거나 구현을 요청할 연동 작업은 없다. 다음 세 가지는 향후 상의할 사항으로만 유지하며 현재 A 화면 개발의 선행 조건으로 두지 않는다.

1. 신규 상품의 최초 재고 및 입출고 이력 생성 규칙
2. B의 입출고 처리 이후 A 목록·상세 화면을 갱신하는 방식
3. 비활성 상품의 신규 입출고 제한과 기존 이력 보존 규칙

대시보드 재계산이나 상품별 판매 요약 제공을 B에게 요청하는 항목은 이번 계획에 포함하지 않는다. 관련 공통 파일을 임의로 수정하거나 존재하지 않는 연동 메서드를 호출하지 않는다.

## 6. 작업 전달 방식

각 단계는 **구현 내용 설명 → 작은 단위 변경 → 실행 확인 → 필요한 설명과 남은 항목 정리** 순서로 진행한다. 첫 구현은 상품 목록과 상세 라우팅부터 시작한다. 한 번에 많은 기능을 넣기보다 단계별로 코드를 이해할 수 있도록 진행한다.

커밋은 화면 연결, 목록·필터와 데이터 가공, CRUD, 상세 화면 단위로 분리한다. 브랜치·커밋·Push·PR은 실제 협업 시점의 사용자 요청에 따라 수행하며 문서 수정만으로 원격 변경을 진행하지 않는다.

최종 전달 시 변경 파일, 실행 결과, 영구 저장 미지원 등 제한 사항과 추후 B와 상의할 세 항목을 정리한다.

## 7. 1차 구현 현황

- Product 목록과 상세 라우팅 연결, 검색·필터·정렬 구현
- Product Controller에서 판매수량·재고 상태·필요수량을 계산하여 화면 전용 JSONModel에 저장
- 별도 폼 모델과 Fragment를 사용한 등록·수정·취소·비활성화 구현
- 신규 상품은 현재 0개 재고로 등록하며 입출고 이력은 생성하지 않음. 최초 재고 규칙은 추후 B와 협의
- 상세 화면의 재고·판매 요약, 상품별 입출고 이력, 없는 상품 처리 구현
- 기본 UI5 컨트롤과 여백 클래스 사용, 공통 CSS·사이드바·타 팀원 코드 변경 없음

검증 결과:

- `npm run build`: 통과. 기존 i18n fallback locale 경고가 있음
- 변경한 두 Controller와 신규 테스트 파일의 ESLint: 통과
- `node --test test/product-controllers.test.cjs`: 데이터 가공·필터·정렬 후 ID 기반 저장·등록 검증·상세 집계·비동기 로딩 등 5개 테스트 통과
- XML View 두 개와 Fragment의 XML 구문 검사: 통과
- `npm run lint`: 수정하지 않은 기존 파일의 줄바꿈 등 오류로 전체 통과하지 못함. 해당 파일은 수정하지 않음
- 실제 UI5 브라우저에서 렌더링·클릭·Dialog 입력 동작은 아직 검증하지 못함. 자동 테스트는 Controller 데이터 처리 검증이며 UI 동작 검증을 대체하지 않음

코드를 읽을 때는 `Product.controller.js`의 `_refreshProducts` → `onFilterChange` → `onCreate`/`onEdit` → `onSave` 순서로 보면 데이터의 흐름을 따라가기 쉽다. 상세는 `_onMatched` → `_loadProduct` 순서로 확인한다.
