> **프로젝트 협업 방향**
> 
> 
> SAPUI5 학습과 단위 프로젝트 완성을 함께 목표로 하며, 기능별 파일 분리를 통해 팀원 간 코드 충돌을 최소화하는 개발 방식.
> 
> A·B는 핵심 업무 기능과 공통 데이터 구조를 담당하고, C·D·E는 대시보드를 세부 영역으로 나누어 각각 SAPUI5 화면 개발과 데이터 바인딩을 경험하는 방향.

# 1. 최종 역할 분담

## 📌 담당 기능 요약

| 담당자 | 담당 영역 | 주요 작업 |

| **B (명진)** | Stock Movement / 공통 데이터 | 입출고 처리, 재고 검증, 공통 모델 및 통계 데이터 관리 |

### 역할 분담 원칙

- 각 담당자는 자신의 XML View와 Controller 파일을 중심으로 개발

- 공통 데이터 계산은 B가 담당하고, 대시보드 담당자는 계산된 데이터를 화면에 연결

- 구현 경험을 위해 D·E는 각각 차트와 테이블을 모두 개발

# 3. SAPUI5 파일 구조 및 담당자

## 📁 Dashboard 파일 분리

대시보드의 각 기능을 별도의 XML View와 Controller로 구성.

| 담당 | View 파일 | Controller 파일 |
| --- | --- | --- |
| C | `dashboard/Kpi.view.xml` | `dashboard/Kpi.controller.js` |
| D | `dashboard/MonthlyChart.view.xml` | `dashboard/MonthlyChart.controller.js` |
| D | `dashboard/LowStockTable.view.xml` | `dashboard/LowStockTable.controller.js` |
| E | `dashboard/CategoryChart.view.xml` | `dashboard/CategoryChart.controller.js` |
| E | `dashboard/Top5Table.view.xml` | `dashboard/Top5Table.controller.js` |

각 하위 View는 독립적으로 작성하며, 최종적으로 `MainView.view.xml`에서 조합.

이 구조를 통해 동일한 대시보드 화면을 개발하더라도 팀원별 수정 파일이 겹치지 않도록 구성.

## 📁 핵심 기능 파일

| 담당 | 파일 | 역할 |
| --- | --- | --- |
| A | `Product.view.xml` | 상품 관리 UI |
| A | `Product.controller.js` | 상품 CRUD·검색·필터 |
| A | `ProductDetail.view.xml` | 상품 상세 UI |
| A | `ProductDetail.controller.js` | 상품 상세정보·이력 조회 |
| B | `StockMovement.view.xml` | 입출고 관리 UI |
| B | `StockMovement.controller.js` | 입출고 처리·재고 갱신 |

## 📁 공통 파일

공통 파일은 담당자를 지정하여 관리.

| 담당 | 파일 | 역할 |
| --- | --- | --- |
| A | `App.view.xml` | 공통 네비게이션 |
| A | `App.controller.js` | 화면 이동 처리 |
| A | `MainView.view.xml` | Dashboard 하위 View 배치 |
| A | `manifest.json` | 앱 라우팅 설정 |
| B | `Component.js` | 공통 모델 초기화 |
| B | `model/mockData.json` | 상품·입출고·카테고리 데이터 |
| B | `util/dashboardData.js` | 대시보드 표시 데이터 계산 |

※ 기존 프로젝트의 `models.js` 등 자동 생성 파일은 역할을 확인한 뒤 필요한 범위에서만 수정

### 파일 수정 규칙

- 원칙적으로 담당자 본인의 파일만 수정
- 공통 파일 변경이 필요한 경우 담당자와 사전 협의
- 동일한 XML·Controller 파일을 여러 명이 동시에 수정하지 않도록 관리
- CSS는 공통 스타일과 기능별 스타일을 구분하고, 신규 스타일 파일 연결은 공통 파일 담당자와 협의

# 4. 공통 데이터 관리 방식

## 📌 데이터 구조

**① inventory 모델 — 원본 데이터**

- `products`: 상품 기본정보 및 현재 재고
- `movements`: 입출고 이력
- `categories`: 카테고리 정보
- `i`: 선택 상품 등 화면 상태

**② dashboard 모델 — 화면 표시용 데이터**

원본 데이터를 기반으로 계산한 결과를 제공하는 모델.

| 제공 데이터 | 사용 담당 |
| --- | --- |
| 전체 상품 수 | C |
| 총 재고 수량 | C |
| 재고 부족 상품 수 | C |
| 이번 달 입출고 수량 | C |
| 월별 입출고 데이터 | D |
| 재고 부족 상품 목록 | D |
| 카테고리별 재고 데이터 | E |
| 인기 상품 TOP 5 | E |

### 데이터 처리 원칙

1. 원본 상품·입출고 데이터는 공통 inventory 모델에서 관리
2. Dashboard에 필요한 계산은 `dashboardData.js`에서 처리
3. C·D·E는 계산 결과를 바인딩하여 화면에 표시
4. 상품 및 재고 변경 후 Dashboard 데이터 재계산
5. 동일한 통계 계산을 여러 Controller에 중복 구현하지 않도록 관리

**데이터 필드명 통일**

최종 설계안에서 수정된 `productId`, `productName`, `stock`, `movementId`, `categoryId` 등을 기준으로 사용.

기존 문서에 남아 있는 `id`, `name`, `currentStock` 등 이전 필드명과 혼용하지 않도록 주의.

**담당: 전체**

| 담당 | 1차 목표 |

**담당: 전체**

# 6. GitHub 협업 규칙

## 브랜치 운영

| 브랜치 | 용도 |
| --- | --- |
| `main` | 최종 안정 버전 |
| `develop` | 기능 통합 및 테스트 |
| 개인별 브랜치 5개 | 담당 기능 개발 |

### 작업 방식

1. A·B가 공통 구조를 준비해 `develop`에 반영
2. 각 팀원이 최신 `develop` 코드를 자신의 브랜치에 반영
3. 본인 담당 파일에서 개발 진행
4. 기능 완성 후 Commit 및 Push
5. `develop`을 대상으로 Pull Request 생성
6. 변경 파일과 실행 결과 확인 후 Merge
7. 전체 기능 테스트 완료 후 `main`에 최종 반영

### 협업 시 유의사항

- `main`에 직접 Push하지 않기
- 담당자가 아닌 공통 파일 임의 수정 금지
- 코드 수정 전 최신 버전 확인
- 기능 단위로 Commit 작성
- 다른 팀원의 파일 수정이 필요하면 사전 공유
- Pull Request 병합 전 실행 오류 확인
- 데이터 필드명은 합의 없이 변경하지 않기
